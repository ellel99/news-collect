## 7. 功能需求

### FR-01 — Adapter Contract

要求：框架定义异步 adapter protocol，adapter 只接收不可变 CollectionTarget、cursor snapshot、batch limit 和 timeout context，并返回 FetchBatch 或抛出 ClassifiedCollectionError。

Adapter contract 不得获得数据库 session、Celery app、Telegram client、管理接口、秘密仓库写权限或任意工具执行权限。Adapter 不得自行写数据库、推进 cursor、调度 retry、发送通知或做 AI 判断。

验收方式：使用至少三个 fake adapter 验证成功、空批次、分页 checkpoint、超时和分类错误；静态类型检查证明 registry 只接受 contract 实现。

### FR-02 — Contract Types

要求：实现阶段定义以下内部契约，名称可按项目风格微调，但语义不得改变：

| Contract | 必需语义 |
|---|---|
| `CollectionTarget` | `source_id`、可空 `source_account_id`、source type、access method 和非秘密 collection options |
| `CursorSnapshot` | cursor type、可空 cursor value、可空 last published time；对 adapter 只读 |
| `FetchRequest` | target、cursor snapshot、batch limit、deadline/cancellation context |
| `RawItemEnvelope` | external ID、fetched time、HTTP status、content type、payload location/hash、retention class 和必要的受限 raw payload contract |
| `FetchBatch` | zero or more envelopes、可空 next cursor、可空 last published time、has more 标记 |
| `ClassifiedCollectionError` | stable error code、retry class、可空 retry-after、可安全记录的 redacted detail |

未知 external ID、cursor 或时间必须为 `None`；不得编造。

验收方式：契约单元测试覆盖不可变性、nullable 语义、非秘密序列化和无未来阶段字段。

### FR-03 — Adapter Registry

要求：registry 通过既有 `Source.access_method` 字段的值作为稳定 adapter key 解析 contract 实现；本 SPEC 不新增 adapter key 字段、enum 或任何其他 schema。未注册、未知、禁用或未授权的 adapter 必须 fail closed；不得自动回退到网页抓取、其他 adapter 或其他访问方式。

实现阶段只允许 `access_method = "fake"` 解析为确定性的测试 adapter，并且该值只用于合成测试数据。真实 adapter key 与来源配置留给 SPEC-0004/0005。

验收方式：验证 `Source.access_method = "fake"` 可解析已注册 fake adapter；未知、未注册、禁用和无授权 target 返回不可重试的配置错误，且不发起网络请求、不 fallback 到网页抓取或其他方式。

### FR-04 — Scheduler Dispatcher

要求：Celery Beat 以固定短周期触发 dispatcher。dispatcher 只查询 enabled Source，并按下列规则形成 CollectionTarget：

1. Source 的 `authorization_status` 只有 `authorized` 或 `implemented` 时才具备调度资格；
2. `planned`、`access_tbd`、`degraded`、`blocked`、`disabled` 均不得进入调度；
3. 具备调度资格的 Source 下存在 enabled SourceAccount 时，为每个 enabled account 形成目标；
4. 没有 SourceAccount 的合格来源可以形成 `source_account_id = NULL` 的 source-level 目标；
5. disabled Source 或 disabled account 永不调度；
6. `schedule_seconds IS NULL` 的来源不自动调度；
7. `access_method` 必须是 registry 已注册且本 SPEC 允许的 `"fake"`；未知、未注册或未授权值 fail closed；
8. due time 使用 UTC，并结合 `last_success_at`、最近 CollectionRun 和连续失败退避计算；
9. 存在同目标 `running` CollectionRun 或有效分布式锁时不得重复派发。

dispatcher 不调用 adapter，不持久化 RawItem，不推进 cursor。

验收方式：冻结时钟测试覆盖首次到期、正常周期、七种 `authorization_status`、未知/未注册 `access_method`、disabled、无 schedule、失败退避、多账号和重复 dispatcher 执行；断言不合格来源不 enqueue 且不发生任何 fallback。

### FR-05 — Dispatch Idempotency

要求：每个派发使用稳定 dispatch key：

```text
source_id : source_account_id-or-source : scheduled_slot
```

scheduled slot 由 UTC 时间和 `schedule_seconds` 确定。重复 dispatcher、Beat 重放或进程重启不得为同一 slot 并发执行同一 target。Celery task ID 或等价幂等键必须由 dispatch key 确定性生成。

验收方式：并发调用 dispatcher 两次，断言同一 target/slot 最多产生一个有效 collection task。

### FR-06 — CollectionRun Lifecycle

要求：worker 获得目标锁后创建一个 CollectionRun。一次逻辑运行的所有 Celery retry 复用同一 `collection_run_id`。

状态语义：

- `running`：已创建，正在执行或等待同一逻辑运行的 retry；`finished_at` 为 null。
- `succeeded`：所有返回批次已安全持久化，包括合法空结果。
- `partial`：至少一个 checkpoint 已持久化，但后续失败在最大尝试后仍未恢复。
- `failed`：没有安全持久化任何 checkpoint，且错误不可重试或 retry 已耗尽。

`finished_at` 只在终态写入。`error_code` 使用稳定分类码，`error_message_redacted` 不得包含 Token、Cookie、完整 URL query、cursor value 或 raw payload。

验收方式：PostgreSQL 集成测试覆盖四种状态、终态时间、retry 复用 run ID 和脱敏错误。

### FR-07 — RawItem Persistence Boundary

要求：框架只将 adapter contract 返回的 RawItemEnvelope 保存为 RawItem；本 SPEC 不解析或标准化 ContentItem。

- 每条 RawItem 必须关联当前 CollectionRun。
- `source_id` 和 `source_account_id` 必须来自当前 target，不接受 adapter 覆盖。
- 受限 payload 按 retention contract 最小化；测试只使用合成 metadata/hash，不保存真实正文。
- RawItem 可以保留重复获取留痕；本 SPEC 不计算 ContentItem 去重。
- 本 SPEC 中 `CollectionRun.new_count` 和 `duplicate_count` 保持 0；其业务语义由 SPEC-0006 实现。
- `fetched_count` 表示 adapter 返回并被框架检查的 envelope 数量。

验收方式：PostgreSQL 集成测试验证 run/source/account 关联、target 字段不可伪造和失败事务不留下孤立 RawItem。

### FR-08 — Cursor Read and Initialization

要求：每个 target 在 adapter 调用前读取 CollectionCursor snapshot。cursor type 由 adapter contract 声明；不存在记录时使用空 snapshot，不预先插入或编造 cursor。

同一 SourceAccount 和 cursor type 只使用 SPEC-0002 的唯一记录。source-level target 没有 SourceAccount 时不得写 CollectionCursor；该类 adapter 必须使用无 cursor contract，直到后续 SPEC 明确数据模型。

验收方式：测试存在 cursor、无 cursor、错误 cursor type、并发读取和 source-level 无 cursor。

### FR-09 — Cursor Checkpoint Atomicity

要求：cursor 只在对应 batch 的全部 RawItem 已安全写入后推进。RawItem 写入和 cursor upsert/update 必须在同一 PostgreSQL 事务中提交。

规则：

1. adapter 返回的 next cursor 只是候选值，无直接写权限；
2. transaction rollback 时 RawItem 与 cursor 都不变；
3. cursor 不得倒退；同一 adapter 定义可比较的单调规则，无法比较时只允许当前 snapshot 的直接 successor；
4. `last_published_at` 不得倒退；
5. 多页采集时每页可作为独立 checkpoint，但只有已提交页面可推进；
6. 失败发生在首个 checkpoint 前时 cursor 完全不变；
7. retry 必须从数据库重新读取最新已提交 cursor，不复用进程内旧 snapshot。

验收方式：故障注入测试覆盖写入前失败、写入中 rollback、commit 后崩溃、分页第二页失败、重复 retry 和 cursor 单调性。

### FR-10 — Concurrency Control

要求：同一 CollectionTarget 同时最多有一个有效 collection execution。实现使用 Redis owner-token lease：

- lock key 只含稳定 UUID/类型，不含秘密；
- 原子 `SET NX PX` 或等价实现；
- value 为每次执行的随机 owner token；
- 长任务在 lease 过半前续期；
- 续期和释放必须原子校验 owner token；
- 非 owner 不得续期或释放；
- worker 崩溃后锁在有限 TTL 内自动释放；
- 获取锁失败不是采集失败，不创建第二个 CollectionRun。

锁 TTL 必须大于单次 adapter timeout，并覆盖合理的数据库提交时间。不得使用永久锁。

验收方式：Redis 集成测试覆盖竞争、续期、错误 owner、崩溃过期和重复 task。

### FR-11 — Timeout and Cancellation

要求：每次 adapter 调用有硬 timeout；一次 task 有总 deadline。timeout 必须取消 adapter 协程、分类为 `COLLECTION_TIMEOUT`，不得继续在后台写入或推进 cursor。

验收方式：可控 fake adapter 阻塞超过 timeout，断言被取消、run 进入 retry 或终态、cursor 未推进且无后台副作用。

### FR-12 — Retry Policy

要求：retry 由框架统一调度，adapter 只返回分类信息。一次逻辑运行默认最多 4 次尝试（首次 + 3 次 retry），可通过无秘密配置收紧，不得无限 retry。

无 Retry-After 时使用 capped exponential full jitter：

```text
delay = random(0, min(max_delay, base_delay * 2 ** retry_count))
```

有合法 Retry-After 时：

```text
delay = min(retry_after, max_retry_after)
```

非法、负数或超过上限的 Retry-After 必须拒绝或截断。测试注入固定随机源和时钟，禁止依赖真实等待。

验收方式：单元测试覆盖 attempt 计数、上限、jitter 边界、Retry-After、耗尽和非重试错误。

### FR-13 — Error Classification

要求：至少使用下表分类。stable error code 写入 CollectionRun，日志只写 redacted context。

| Error Code | 典型条件 | Retry | 调度表现 |
|---|---|---|---|
| `COLLECTION_TIMEOUT` | adapter 超时 | 是 | 指数退避 |
| `COLLECTION_NETWORK` | DNS、连接重置、临时网络失败 | 是 | 指数退避 |
| `COLLECTION_RATE_LIMITED` | HTTP 429 或明确限流 | 是 | 优先使用合法 Retry-After |
| `COLLECTION_UPSTREAM_5XX` | 上游 5xx | 是 | 指数退避 |
| `COLLECTION_UPSTREAM_RETRYABLE` | HTTP 408/425 或经 contract 明确的临时错误 | 是 | 指数退避 |
| `COLLECTION_DATABASE_UNAVAILABLE` | 数据库临时不可用 | 是 | 指数退避；cursor 不推进 |
| `COLLECTION_LOCK_LOST` | owner lease 丢失 | 是 | 立即停止写入；重新排队由框架决定 |
| `COLLECTION_AUTH` | 缺失/失效授权 | 否 | failed；不得绕过或换接入方式 |
| `COLLECTION_FORBIDDEN` | HTTP 401/403、访问控制 | 否 | failed；等待人工处理 |
| `COLLECTION_NOT_FOUND` | HTTP 404/410 | 否 | failed；等待来源核验 |
| `COLLECTION_CONTRACT_INVALID` | adapter 返回非法 batch/cursor/envelope | 否 | failed；开发错误可见 |
| `COLLECTION_CONFIG_INVALID` | 未注册 adapter、无 schedule 或配置非法 | 否 | 不执行或 failed，记录稳定错误 |
| `COLLECTION_CANCELLED` | 部署关闭或显式取消 | 否 | 安全停止；未提交 checkpoint 不推进 |
| `COLLECTION_STALE_RUN` | `running` CollectionRun 超过 stale 阈值，且无有效 task/lock | 否 | failed；由 `recover_stale_runs` 标记；不推进 cursor |
| `COLLECTION_UNKNOWN` | 未分类异常 | 否 | failed；不得盲目 retry |

验收方式：参数化测试证明每个错误码的 retry 决策、run 终态和日志脱敏符合表格。

### FR-14 — Failure Backoff and Source Health

要求：

- 成功终态：更新 Source `last_success_at`，将 `consecutive_failures` 置 0。
- partial/failed 终态：不更新 `last_success_at`，原子增加 `consecutive_failures`。
- scheduler 对失败来源使用基于 `consecutive_failures` 的 capped backoff，避免每个 Beat tick 立即重派。
- 单一来源失败不得阻塞其他来源。
- 只有成功完成 source-level 目标或该轮全部已派发 account targets 成功时，才更新 source-level success；实现必须避免某一个账号成功掩盖同源其他账号失败。

验收方式：多来源和多账号集成测试验证成功复位、失败递增、单源隔离和 source-level success 语义。

### FR-15 — Restart Recovery

要求：worker 重启后不得依赖内存 cursor 或 retry state。

- retry task 通过 `collection_run_id` 重新加载 CollectionRun 和最新 cursor；
- 过期 Redis lock 自动释放；
- 数据库中长期停留 `running` 且超过 stale 阈值、无有效 task/lock 的 run，必须由恢复扫描标记为 failed，错误码必须为 `COLLECTION_STALE_RUN`；
- 恢复扫描只修正明确过期的 run，不猜测未完成结果，不推进 cursor。

验收方式：模拟 worker 在 fetch 前、事务中、commit 后和 retry 前终止，验证恢复后不丢 checkpoint、不重复推进 cursor；明确断言超过阈值且无有效 task/lock 的 run 被标记为 failed、`error_code = "COLLECTION_STALE_RUN"` 且 cursor 不变。

### FR-16 — Observability

要求：结构化日志至少包含 `task_id`、`collection_run_id`、`source_id`、可空 `source_account_id`、attempt、error code、duration、fetched count 和 checkpoint count。

禁止记录 Token、Cookie、Authorization header、完整 cursor、raw payload、完整正文或未脱敏异常。指标接口不在本 SPEC；测试验证可观测字段和脱敏。

验收方式：捕获成功、retry、失败和 lock contention 日志，验证字段完整且秘密/载荷不存在。

## 8. 非功能需求

- 可靠性：至少一次 task 交付下，数据库写入和 cursor 推进仍安全；重启后从持久化 checkpoint 恢复。
- 性能：dispatcher 查询必须有界；默认单次 batch limit 不超过配置上限；不得一次加载全部 Source/Run 历史。
- 并发：同 target 单执行，不同 target 可并发；单源故障不影响其他来源。
- 安全：外部内容始终是不可信数据；adapter 无工具、管理和通知权限；日志、错误和锁键脱敏。
- 可观测性：所有运行有 CollectionRun；失败必须有稳定 error code，不能表现为“没有新消息”。
- 合规：只使用 fake adapter 和合成数据，不验证或暗示任何真实来源授权。
- 可测试性：时钟、随机源、adapter registry、lock backend 和 task enqueue 必须可注入替换。

### Celery Tasks

| Task | 责任 | 不允许 |
|---|---|---|
| `collection.dispatch_due_targets` | 查询到期 target 并幂等 enqueue | 调用 adapter、写 RawItem、推进 cursor |
| `collection.run_target` | 锁定 target、维护 run、调用 fake adapter、持久化 batch、分类 retry | 真实来源、标准化、通知 |
| `collection.recover_stale_runs` | 标记明确过期且无有效 lock 的 running run | 猜测成功、推进 cursor |

### Beat Schedule

- dispatcher：默认每 30 秒运行一次。
- stale run recovery：默认每 5 分钟运行一次。
- 配置必须允许在测试中禁用 Beat 或使用 eager/fake queue。
- 不引入数据库调度表。

### API / CLI / Bot / 外部消息

- API：无。
- CLI：无。
- Bot：无。
- Outbox/外部队列消息：无；Celery 内部 task 不等同于业务 Outbox。

## 12. 错误处理

错误分类和 retry 决策以 FR-13 为唯一表格。额外规则：

- 所有未知异常 fail closed 为 `COLLECTION_UNKNOWN`，不得默认 retry。
- 错误 detail 在进入日志和 CollectionRun 前统一脱敏与长度限制。
- 数据库事务失败后必须 rollback；cursor 和 RawItem 要么一起提交，要么一起不提交。
- lock lost 后禁止继续数据库写入。
- task retry enqueue 失败时，当前 run 必须最终可由 stale recovery 识别，不能静默遗留。

## 13. Migration and Rollback

- 升级：无数据库迁移。实现只增加可删除的框架模块、配置模板、Celery task 注册和测试。
- 回滚：移除 SPEC-0003 框架/task/配置，恢复 SPEC-0002 的空 Beat schedule；数据库 schema 和既有数据不变。
- 数据兼容：只使用既有字段。框架写入的 CollectionRun、RawItem 和 Cursor 是 Phase 1 合法数据；代码回滚前应停止 worker，避免旧 task 被新/旧代码混合消费。
- 部署回滚：先暂停 Beat 和 worker，等待或终止运行任务，确认无正在提交的 checkpoint，再回滚代码并重启。
- 备份要求：本 SPEC 无 schema 变化；实现验收仍需确认测试数据和本地数据库不进入 Git/Review ZIP。
