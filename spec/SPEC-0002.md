# SPEC-0002 — Source Registry and Phase 1 Data Model

状态：Active（仅规格文档已激活；实现须在本文档 Review PASS 后开始）
阶段：Phase 1 — Information Collection & Push
负责人：Project Owner
创建日期：2026-07-29
最后更新：2026-07-29

## 1. 目标

在不引入采集、推送或后续阶段能力的前提下，交付 Source Registry 与九个 Phase 1 实体的 PostgreSQL 16 持久化模型、约束、索引和可逆 Alembic 迁移，为后续采集链路提供唯一且可审计的数据契约。

## 2. 背景

SPEC-0001 已完成项目骨架、基础设施和仅含 `system_metadata` 的基础迁移。Roadmap 的下一项是 Source Registry and Phase 1 Data Model。当前需要先固定 Phase 1 持久化边界，避免后续适配器、调度、标准化和通知 SPEC 各自发明不兼容的数据结构。

本文档被设为唯一 Active SPEC，但本次文档 PR 不授权实现。只有本文档经用户或 Reviewer 审核并明确 PASS 后，才可创建实现分支并执行第 13 节任务。

## 3. Foundation 与阶段边界

- 使用的冻结 Decision：Foundation v2.1-FROZEN、Phase 1 Content First、Broad Scan、Controlled Push、PostgreSQL 16 和 SQLAlchemy 2.x/Alembic 技术基线。
- 当前阶段允许：`Source`、`SourceAccount`、`CollectionCursor`、`CollectionRun`、`RawItem`、`ContentItem`、`Notification`、`OutboxMessage`、`AuditLog`。
- 当前阶段禁止：LLM、Embedding、向量数据库、AI 翻译/摘要/分类、`Event`、`Evidence`、`Analysis`、`Portfolio`、`Holding`、`InvestmentPlan`、`CandidateRule`、交易建议和自动交易。
- 本 SPEC 不得以“未来需要”为理由创建任何 Phase 2–4 表、依赖、服务或空引擎。
- 是否修改 Foundation：否。

## 4. 前置条件与依赖

- 前置 SPEC：SPEC-0001 已完成并合并，tag 为 `spec-0001-completed`。
- 外部权限：无；本 SPEC 不连接任何真实来源，也不确认任何来源授权状态。
- 基础设施：SPEC-0001 的 Python 3.12、PostgreSQL 16、SQLAlchemy 2.x、Alembic、pytest 和 Docker Compose。
- 需要用户确认的事项：本文档的数据契约、约束和迁移方案必须 Review PASS 后才允许实现。

## 5. 范围

- 为第 8 节列出的九个 Phase 1 实体建立 SQLAlchemy 2.x ORM 模型。
- 使用 PostgreSQL 原生 `uuid`、带时区时间、JSONB、检查约束、外键、唯一约束和索引。
- 新建一条可升级、可降级、可重复往返的 Alembic 迁移；保留 SPEC-0001 的 `system_metadata`。
- 建立 Source Registry 的来源、账号、授权/保留状态和调度元数据的数据契约。
- 建立后续采集、标准化、通知和审计 SPEC 所需的持久化结构，但不实现这些流程。
- 为模型、约束和迁移提供 PostgreSQL 集成测试。
- 更新与实际实现直接相关的模型文档、变更记录和交付报告。

## 6. 非范围

- 不实现 Source 或 SourceAccount 的 API、CLI、管理界面、service、repository 或 CRUD 工作流。
- 不实现 adapter、collector、scheduler、Celery task、cursor 推进、retry、补采或来源健康计算。
- 不接入或预置真实新闻源、RSS、API、网页、X 或 Telegram，不编造 URL、账号 ID、授权状态或 API 能力。
- 不实现 RawItem 获取、ContentItem 标准化、确定性去重、Notification 策略、Outbox 发布或 Telegram 投递。
- 不保存真实原始正文、Token、Cookie、API Key、私钥或本地数据库。
- 不实现 AI/LLM、Event、Evidence、Analysis、Portfolio、Holding、Investment Plan、Candidate Rule 或任何 Phase 2–4 表。
- 不修改 Foundation v2.1-FROZEN，不回改 SPEC-0001，除非另有明确 bugfix 授权。

## 7. 功能需求

### FR-01 — Phase 1 模型边界

要求：ORM metadata 和迁移只新增第 8 节明确列出的九张表，不得出现 Phase 2–4 实体或其他预留业务表。

验收方式：检查 Alembic revision、SQLAlchemy metadata 和 PostgreSQL 实际 schema；针对允许表集合与禁止名称编写测试。

### FR-02 — Source Registry

要求：`sources` 和 `source_accounts` 能保存逻辑来源、来源下账号/栏目/Feed/端点、访问方式、授权状态、保留等级、启停状态和采集配置元数据。未知稳定外部 ID 必须为 `NULL`，不得编造。

验收方式：在 PostgreSQL 中插入最小的未知来源 fixture，验证外键、枚举/检查约束、唯一约束、JSONB 默认值和 nullable 规则。

### FR-03 — 采集持久化契约

要求：`collection_cursors`、`collection_runs` 和 `raw_items` 提供后续 SPEC 所需的游标、运行统计、可分类错误和原始获取元数据结构；本 SPEC 不实现运行行为。

验收方式：模型与数据库 schema 一致性测试，并验证非负计数、状态范围和外键约束。

### FR-04 — Content First 契约

要求：`content_items` 保存来源直接提供的内容与时间。来源摘要字段必须命名为 `source_summary`；不得出现 `ai_summary`、Event 外键或模糊语义去重字段。

验收方式：验证字段名、内容状态约束和三层确定性唯一性规则。

### FR-05 — 通知与可靠发布契约

要求：`notifications` 和 `outbox_messages` 仅提供 Phase 1 确定性通知和可靠发布的数据结构；不得实现投递器、Telegram Bot 或消息消费任务。

验收方式：验证 P0–P4、状态范围、幂等键、可用时间和重试计数约束。

### FR-06 — 审计契约

要求：`audit_logs` 保存脱敏的关键状态变化信息。数据库关系不得要求保存秘密或完整敏感正文。

验收方式：验证目标/动作字段、JSONB 前后值、创建时间和必要索引。

### FR-07 — 可逆迁移

要求：迁移可从 SPEC-0001 的 head 升级至 SPEC-0002 head，降级一版后只移除本 SPEC 新增对象，再次升级成功。

验收方式：在 PostgreSQL 16 上执行 `upgrade head → downgrade -1 → upgrade head`，并检查 `system_metadata` 始终存在。

## 8. 数据模型变化

### 8.1 通用约定

- 表名和字段名使用 `snake_case`，主键为数据库生成的 UUID。
- 所有时间使用 PostgreSQL `timestamp with time zone` 并以 UTC 写入；必填创建时间使用数据库默认值。
- 可扩展结构使用 JSONB，非空 JSONB 字段默认 `{}`。
- 字符串状态使用命名 PostgreSQL enum 或等价检查约束；迁移降级必须删除本 revision 创建的 enum。
- 所有计数必须大于等于 0；`schedule_seconds` 大于 0。
- 外键默认 `ON DELETE RESTRICT`，不得通过级联删除破坏原始留痕和审计。
- `created_at` 创建后不可修改；带 `updated_at` 的模型在修改时更新时间。
- 迁移不写入真实来源或账号 seed data。

| `id` | UUID，非空 | 主键 |
| `code` | varchar(100)，非空 | 唯一、稳定、非空白 |

| `source_type` | enum，非空 | `news`, `x`, `official`, `rss`, `api`, `web` |
| `access_method` | varchar(100)，非空 | 仅记录已确认方式；未知用 `unknown` |
| `authorization_status` | enum，非空 | `planned`, `access_tbd`, `authorized`, `implemented`, `degraded`, `blocked`, `disabled` |
| `retention_class` | varchar(50)，非空 | 保留策略标识；不在本 SPEC 固定保留天数 |
| `enabled` | boolean，非空 | 默认 `false`，避免未审核来源自动启用 |
| `schedule_seconds` | integer，可空 | 大于 0；未配置时为 `NULL` |
| `last_success_at` | timestamptz，可空 | 仅由后续采集 SPEC 更新 |

## 11. 错误处理

| Error Code | 条件 | 是否重试 | 用户/运维表现 |
|---|---|---|---|
| `DATA_INTEGRITY_VIOLATION` | 唯一、外键或检查约束失败 | 否 | 回滚事务；日志只记录约束名和关联 ID，不记录正文或秘密 |
| `MIGRATION_FAILED` | Alembic 升级或降级失败 | 否 | 命令非零退出；保留数据库日志供排错 |
| `DATABASE_UNAVAILABLE` | PostgreSQL 不可连接 | 是，由调用方决定 | 使用 SPEC-0001 的脱敏数据库错误表现 |

本 SPEC 不实现业务异常映射层；上表定义实现与测试必须验证的数据库边界。

## 12. Migration and Rollback

- 升级：在 SPEC-0001 Alembic head 之后新增单一 revision，按外键依赖顺序创建 enum、九张表、约束和索引。
- 回滚：按依赖逆序删除本 SPEC 的九张表、索引和本 revision 创建的 enum；不得删除或重建 `system_metadata`。
- 往返验证：在 PostgreSQL 16 上执行 `uv run alembic upgrade head`、`uv run alembic downgrade -1`、`uv run alembic upgrade head`，每一步检查实际表集合。
- 数据兼容：升级不修改 SPEC-0001 数据；降级会删除本 SPEC 表及其中数据，只用于开发/空库验收。非空环境降级前必须备份并明确接受数据丢失。
- 备份要求：实现交付报告必须记录测试环境为空库或备份位置；备份文件不得进入 Git 或 Review ZIP。
- 迁移原子性：在 PostgreSQL 支持范围内使用事务性 DDL；失败必须保持 revision 状态可诊断。
